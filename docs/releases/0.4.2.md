# Usage Pace 0.4.2 — draft release notes

Patch release for the remaining 0.4.1 account-merging gap with bb 0.46.1's cached last-success timestamps on failed reads.

## Fixes

- **Healthy quota wins over failed duplicates.** Merged accounts prefer the newest healthy (`status: "ok"`, not stale) measurement, even when a failed source reports a newer last-success timestamp. A transient machine read failure no longer makes a healthy merged account stale or turns a two-account pool into `1/2 available · 1 unknown`.
- **Known accounts keep their metadata through errors.** When an error keeps the resource's known identity but omits email, plan, or plan label, retain the cached fields. Email-based aliases and plan weights remain available. Explicit identity changes still discard the old account's metadata and windows; never-known identities remain separate.
- **Failures remain visible and honest.** Merged hosts, sources, and source-error messages remain visible. An account whose only source fails stays stale and counts as unknown despite retaining its alias and plan. When all sources are stale, the newest observation still wins.

Release artifacts remain built with **BB 0.44.0 / SDK 0.5.29**; minimum requirements are unchanged. Saved resets remain read-only. The CLI JSON accounts/providers alias, nullable pace, token totals, and Codex-only `--resets` behavior are unchanged.

## New installations

After 0.4.2 is published:

```sh
bb plugin install 'git:https://github.com/scowalt/bb-plugin-usage-pace.git@v0.4.2'
bb plugin config usage-pace set showStrip true
```

The second command enables the optional strip. Use `@^0.4.2` instead of the exact tag to track compatible releases.

## Upgrades

Inspect the requested and resolved source first:

```sh
bb plugin source usage-pace
```

For repository/branch-tracking installs whose branch contains 0.4.2, or a release-range install that admits the published tag, update in place and keep settings:

```sh
bb plugin update usage-pace
```

An exact tag or commit does not advance to a newer tag with `update`. Moving a pinned install, or changing an existing install to a tag or range, requires removal first. **Removal deletes settings, secrets, and schedules.** Record the current configuration and restore your settings after reinstalling:

```sh
bb plugin config usage-pace
bb plugin remove usage-pace
bb plugin install 'git:https://github.com/scowalt/bb-plugin-usage-pace.git@v0.4.2'
```

Use `@^0.4.2` in the final command for compatible-release tracking. Do not use `plugin install` as an in-place upgrade: bb 0.46.1 rejects the duplicate plugin ID.

## Verification boundary

The realistic timestamp reproduction, sole-source failure, all-stale fallback, and before/after test evidence are recorded in [multi-account verification](../plans/multi-account-verification.md). Only synthetic identities and `example.test` addresses are used. Both servers' installed plugins and configuration remain untouched. This preparation stops at an open PR: no merge, tag, or GitHub release is published yet, and live 0.4.2 acceptance is separate follow-up work.
